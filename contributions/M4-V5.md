## Contrat V5 à respecter

La connexion étudiante porte une identité commune ; le middleware du lot M3 résout ensuite une adhésion propre au restaurant courant. Pour un étudiant, req.user.id représente cette adhésion locale. Les commandes et les autorisations M4 doivent continuer à l’utiliser, sans remplacement par un identifiant global.

Les identifiants, la photo et les préférences peuvent être partagés ; commandes, points, parrainages, participations et panier restent séparés par restaurant. Le panier côté étudiant est séparé par slug et relève de student.jsx (M3). Les anciens comptes de même adresse ne sont pas fusionnés automatiquement.

## Revue de source effectuée sur M4

Fichier examiné : backend/src/orders.js, blob 922de9d649f06b13bb785dab700a9e732be8c153.

| Point | Constat dans le code de la branche |
| --- | --- |
| Liste des commandes | Filtre restaurant_id avec req.restaurant.id ; pour un étudiant, filtre user_id avec req.user.id. |
| Détail d’une commande | Vérifie le restaurant courant et, pour un étudiant, le propriétaire local avant de renvoyer le JSON. |
| Création | Enregistre req.restaurant.id et req.user.id ; sélectionne chaque article dans le restaurant courant, sans article archivé et avec contrôle de disponibilité. |
| Anti-doublon | La clé de requête est recherchée avec le user_id local ; le verrou utilisateur et la transaction sont conservés. |
| Calculs et récompenses | Les règles sont sélectionnées pour req.restaurant.id ; réservations de points et commandes gardent le user_id local. |
| Personnel | Les routes M4 continuent à dépendre des rôles et du middleware M3, qui doit refuser un changement de restaurant non autorisé. |

Ces constats décrivent le code M4 ; ils ne constituent pas un test d’intégration du nouveau middleware ni une validation des règles complètes.

## Recette à exécuter après assemblage

Tous les scénarios suivants sont À EXÉCUTER avec des données fictives ; aucun résultat de navigateur/API n’est annoncé ici.

| Scénario | Résultat attendu |
| --- | --- |
| Étudiant connecté : choisir A puis B sans reconnexion | Même connexion, adhésions et données métier locales distinctes. |
| Créer une commande dans B puis demander son détail depuis A | Accès refusé ; aucune ligne de commande ni information de paiement de B renvoyée. |
| Commander depuis A un identifiant d’article appartenant à B | Refus sans création de commande ni réservation de points. |
| Remplir le panier de A puis changer vers B | Les articles et totaux de A ne deviennent pas le panier de B. |
| Rejouer une demande de commande dans le même restaurant | Une seule commande et une seule réservation de points. |
| Consulter historique et points dans A puis B | Les commandes et soldes restent propres à chaque établissement. |
| Personnel de A : demander la gestion de B | Refus côté serveur, même avec une URL saisie directement. |
| Ancien compte homonyme dans un autre restaurant | Aucune fusion ou attribution automatique de ses données. |

Après assemblage : exécuter npm ci et npm run check, puis la recette navigateur et la relecture prévue. Le rapport de 103 tests du paquet concerne sa copie de référence ; ces 103 tests n’ont pas été relancés sur la branche officielle M4 dans cette revue.
